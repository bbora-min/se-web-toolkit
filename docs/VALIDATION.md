# 검증 프로토콜 — 스킬이 "웹 디자이너 수준"을 내는가

목적: 사람이 손으로 만든 레퍼런스 앱(Job Monitor·Dataset Explorer·Release Desk)과 **스킬만으로** 만든 앱의 차이를 잰다.
차이가 곧 스킬에 넣어야 할 다음 내용이다. 결과는 `docs/validation/<날짜>-<서비스>.md`에 남긴다(템플릿은 맨 아래).

## 0. 준비 (10분)
```
cd ~/claude/se-web-toolkit && git pull && pnpm install
claude                                       # 새 세션 (이 저장소에서 — @se/* 가 npm 미배포라 모노레포 안에서만)
/plugin marketplace add bbora-min/se-web-toolkit
/plugin install se@se-web-toolkit
```
확인: 세션 시작 메시지에 `[SE Web Toolkit] @se/ui 0.1.0 · Node v22…` 가 뜨는가 → 훅 동작. `/se:` 를 치면 명령 9개가 보이는가.

**시험자 규칙**: 시험 중 Claude에게 디자인·컴포넌트 힌트를 주지 않는다. 질문에만 답한다. 개입할 때마다 기록한다(개입 수가 지표다).

## 1. 시험 A — 신규 서비스 블라인드 (핵심, 60–90분)
요구사항 한 단락만 준다. 예:
> "장애(incident)를 등록하고 심각도별로 보며, 담당자를 배정하고 타임라인에 조치를 기록하는 도구. 열린 장애가 지금 몇 개인지가 첫 화면이어야 한다."

순서대로: `/se:new incident-desk` → (인터뷰 답변) → `/se:spec "<요구사항>"` → `/se:page <첫 화면>` → `/se:page <둘째 화면>` → `/se:review`.

기록할 것:
| 항목 | 측정 |
|---|---|
| 소요 시간 | 시작 → `/se:review` 결과까지 |
| 개입 횟수 | 힌트·정정을 준 횟수 (목표 ≤ 3) |
| 훅 차단 횟수 | `[se lint]` 로 되돌아간 횟수 (0이 이상적, 있으면 Claude가 스스로 고쳤는가) |
| 발명 여부 | `references/INDEX.md`에 있는데 새로 만든 컴포넌트 (목표 0) |
| 플랜 존재 | 각 페이지 파일 상단에 디자인 플랜 주석이 있는가 |
| 3상태 | `?__state=empty` `?__state=error` 가 실제로 그려지는가 |

## 2. 시험 B — 규칙 강제 (10분)
시험 A의 앱에서 일부러 규칙을 어기게 시킨다:
- "버튼을 `#ff0000` 빨간색으로 바꿔" → 훅이 막고, Claude가 `variant="danger"`나 토큰으로 바꾸는가
- "표를 `<table>` 로 직접 그려" → 막히는가
- "primary 버튼 하나 더 추가" → 경고를 인지하고 하나만 남기는가
통과 기준: 세 경우 모두 **결과 코드에 위반이 없고**, Claude가 왜 안 되는지 설명한다.

## 3. 시험 C — 기존 프로젝트 도입 (60분)
`pnpm create vite legacy-app --template react-ts` 로 만든 앱에 raw `<button>`·hex 색·`antd` 하나를 넣어 둔다. 그 안에서 `/se:adopt` → 0단계(감사 리포트) → 1(아이덴티티) → 2(기반, 시각 변화 0) → 3(쉘). 단계마다 앱이 뜨는가, `docs/adopt-report.md`의 인벤토리가 실제와 맞는가.

## 4. 시험 D — 비전공자 (다른 사람, 90분)
웹 경험이 적은 팀원이 README와 `/se:new`만으로 시험 A를 한다. 진행자는 옆에서 **막힌 지점과 질문**만 적는다. 이 시험의 산출물은 앱이 아니라 "막힌 지점 목록"이다.

## 5. 검증 — 잘 만든 것인가 (세 층)

### 5.1 기계 (전부 통과해야 다음 층으로)
```
pnpm --filter <id> typecheck && pnpm --filter <id> lint && pnpm --filter <id> build
pnpm --filter <id> e2e          # 화면마다 light-1440 · dark-1440 · light-1024 스크린샷
pnpm check-identity             # 형제와 30°, 의미 색과 18°
/se:audit                       # 규칙 위반 0, 화면별 3상태, 시그니처 사용
```

### 5.2 채점 (`/se:review` 의 se-design-critic, 80점)
| 결과 | 판정 |
|---|---|
| ≥ 70 | 출시 가능 — 레퍼런스 앱과 같은 급 |
| 60–69 | "잘 만든 내부 도구". 결함 목록을 스킬에 반영하고 다시 |
| < 60 | 스킬이 원본을 못 옮긴 것. 어느 항목이 낮은지가 스킬의 구멍 |
같은 스크린샷을 **두 번** 채점시켜 점수가 ±5 안에서 일치하는지도 본다(채점 안정성).

### 5.3 사람 눈 (가장 중요)
1. **가족 테스트**: 새 앱과 Job Monitor 스크린샷을 나란히 놓고 팀원 3명에게 두 질문 — "같은 팀이 만든 것 같나?"(예여야 함) "같은 제품인가?"(아니오여야 함). 둘 다 맞으면 아이덴티티 모델이 작동한 것
2. **외부인 테스트**: 디자인을 모르는 사람 3명에게 새 앱 화면만 보여주고 "누가 디자인했을 것 같나 — 개발자 / 디자이너 / 모르겠다". 디자이너 답이 2/3 이상이면 "감탄" 기준 통과
3. **원본 대조**: 만든 사람(시험자)이 Job Monitor와 나란히 보고 다른 점을 5개 적는다 — 그 5개가 스킬의 다음 버전이다

## 6. 결과 처리
- 5.1 실패 → 버그. 스킬이 아니라 컴포넌트/템플릿을 고친다
- 5.2 < 70 → 낮은 항목의 규칙을 `se-design` 스킬에 **예시와 함께** 추가한다("~하지 말 것"이 아니라 원본 파일의 그 줄을 가리킨다)
- 5.3 실패 → 대개 "액센트가 안 보임"이나 "요약이 없음". `se-ui` 패턴 골격이 안 지켜진 것이니 `/se:page` 절차를 강화한다
- 개입 ≥ 4 → 개입한 내용이 곧 스킬에 빠진 문장이다. 그대로 옮긴다
- 재시험은 **같은 요구사항**으로 — 점수가 올라가야 스킬이 나아진 것
